# How Spindle works

The rules the code follows, for anyone changing it. How split entries and agent logs work is in
[splits-and-suggestions.md](splits-and-suggestions.md); the Apple apps are described in [apple/README.md](../apple/README.md).

## Conventions

- **IDs** are GUIDs created by the client or the domain, not by the database, so clients can create records offline.
- **Synced tables** derive from `Entity`: `CreatedAt`, `UpdatedAt`, `DeletedAt` and a concurrency token `Version` mapped to PostgreSQL’s `xmin`. It detects stale writes; it is not a global sync cursor.
- **Conditional entry writes**: time entries carry their `version` (opaque text). Updating, stopping or deleting one with `If-Match` set to it (as an entity tag, `"123"`, or bare) goes through only if the entry still has that version; otherwise the answer is 412 with the problem type `urn:spindle:problem:entry-changed` and the entry as it is now in `current`, so the app can show both and let the person choose. The check is the `xmin` in the UPDATE's WHERE clause, so a write saved between reading and writing also fails it. Stopping again at the same time after a lost answer still succeeds. Writes without `If-Match` go through as they always have, for apps that predate it. Bulk changes take no condition: they are made online, on the entries in front of the person, and change only the fields named. The apps' outboxes send the version their change was made on and turn a 412 into a conflict the person settles (see the apps' READMEs). The web sends the version it loaded when it saves or deletes an entry from the editor, deletes one from the list or stops the timer; on a 412 it asks whether to keep the person's version or the other device's, and stops a timer that was only changed elsewhere anyway. Removing an entity through EF writes a tombstone (`DeletedAt`) instead of deleting the row, and a global query filter hides tombstones.
- **Authentication**: JWT access tokens (15 minutes) and one refresh token chain per signed-in device (90 days, rotated on every use). Reusing an old refresh token revokes that device's session. A retry within 30 seconds is allowed, for clients that lost the response.
  - The apps use `/api/auth/*` and keep the refresh token in the Keychain.
  - The web app uses `/api/auth/web/*`. There the refresh token is an HttpOnly, `SameSite=Strict` cookie that scripts cannot read, and the access token stays in memory. After a reload the app renews it from the cookie. Tabs take turns renewing (Web Locks) and tell each other when one signs out.
  - **Passkeys**: add or remove them under Account → Passkeys on the web or Mac, or Settings → Security → Passkeys on iPhone, then use “Sign in with a passkey” without entering an email or password. Adding a key requires the current password; up to ten keys can be registered. The web requires a current browser with WebAuthn JSON support and HTTPS (localhost also works). The Apple apps use AuthenticationServices and keep refresh tokens in Keychain; their passkey controls are available when the build uses the associated production HTTPS domain. The password remains available for recovery and account deletion.
  - Native sign-in uses `/api/auth/passkeys/*`, with an opaque, expiring challenge token in place of the web's browser cookie. It shares the same credential verification, account lockout checks and device sessions. `/.well-known/apple-app-site-association` associates the production domain with the Mac and iPhone app identifiers. See `apple/README.md` for signing and deployment requirements.
  - **Google and Apple** (`ExternalSignInEndpoints`, configured under `Auth:Google` and `Auth:Apple`, offered in `GET /api/server` as `signInProviders`): the server is the OpenID Connect client with the secret, so every app works with any server and a self-hoster brings their own credentials. A browser or app opens `/api/auth/external/{provider}/start`; the provider comes back to `/callback` (Google with a GET, Apple posting a form), and the server checks the ID token's signature, issuer, audience and nonce, then redirects with a one-time code that lives two minutes in `ExternalSignInCodes`. The code is worth a session only with the secret of the client that started: the web's `SameSite=Strict` cookie (`/api/auth/web/external/exchange`) or the app's PKCE verifier (`/api/auth/external/exchange`; Mac, iPhone and Android come back to `spindle://auth/callback`, Windows to a loopback address). So a caught code is useless, and nobody can sign someone else in to their own account. The state that travels through the provider is sealed with Data Protection and lasts ten minutes. A login seen before signs in to its account; otherwise the provider's confirmed email decides: it joins the account with that address or creates one (by invitation only on a closed server). Only an address whose mailbox the provider runs joins an existing account (Gmail or the Workspace domain in Google's `hd`; Apple's relay and iCloud), since another address was only checked when the provider's account was made and may have changed hands; it makes a new, unconfirmed account that confirms by email. An account with the address that was never confirmed loses its password, passkeys and sessions first, since whoever chose them may not own the address; the other way round, a password reset on an unconfirmed account removes its Google and Apple logins and passkeys. Accounts made this way have no password: they set one from a password reset email, and to add a passkey or delete the account they must have signed in on that device in the last ten minutes, in a session that is still signed in (`RecentSignIn`). A login can be removed only while another way to sign in remains.
  - Passkey verification uses ASP.NET Core Identity. The relying party ID and the exact allowed browser origin come from `App:BaseUrl`, including its port in development. Keep that hostname stable: a passkey created on one hostname cannot authenticate on another. Challenges live in PostgreSQL for five minutes and are atomically deleted on use, with an opaque HttpOnly, `SameSite=Strict` cookie binding them to the browser. Registration state is also tied to the signed-in user and their security stamp. Account deletion removes all passkeys and pending registration challenges.
- **Workspaces**: everything a user tracks lives under `/api/workspaces/{workspaceId}/…`. A filter checks membership first; to anyone else the workspace does not exist (404).
- **Time entries** store their tag IDs as a native `uuid[]` array in the entry's own row, so changing tags changes the entry's `Version` and syncs like any other edit. A user has at most one running entry, enforced by a filtered unique index.
- **Database**: PostgreSQL 18, UTC `timestamptz` instants at microsecond precision, and `citext` for case-insensitive catalog names. The `citext` extension is created by the initial migration.
- **Errors** are RFC 9457 problem details. Validation error keys match the JSON property names. A broken domain rule (`DomainValidationException`) becomes a 400 next to the offending field.
- **Time zones** are IANA IDs (`Europe/Zagreb`), validated with NodaTime's bundled database, so the result does not depend on the server OS.
- **Reports** count finished entries by the day they start, in the viewer's time zone. Each entry is rounded first (if asked), then billed at the most specific rate on its day: the person's rate on the project, the project's rate, the person's rate in the workspace, then the workspace default. Amounts are rounded to the cent per entry, so every total adds up. Members see only their own time and no money.
- **Rates have a history** (`Rates` table): each billable rate and labor cost is a list of periods, each from a first day on. A rate changed with a date (`hourlyRateFrom`, `laborCostFrom`, `defaultHourlyRateFrom`) starts a new period, so earlier time keeps its rate; changed without one, the newest period is corrected. Taking someone off a project ends their rate there after today. Admins list and remove periods under `/rates`.
- **Billed time**: a project can have its billed time entered separately (`separateBilledTime`). Admins and its managers then enter, per member and day, the time billed to the client, e.g. to include calls nobody tracked (`/projects/{id}/billing`). Days without an entry are billed as tracked. Reports add the difference as billing adjustments: they change the billed time (`billedSeconds`) and the amount, never the tracked time or labor cost, and are not entries in the detailed report.
- **Timesheet links** (`SharedReports`, `/shared-reports` for admins, `/api/shared/{token}` for anyone): a report's filter and period (this or last week or month, or fixed days), worked out again whenever the link is opened, in the time zone of whoever last saved it. They count billable time only, as billed: days entered separately count as entered, one row per day, project and optionally person, described by the day's entries or by the text entered for that day in the Billing card (`BilledTime.Description`), except on links narrowed to tasks, tags or descriptions, which show only their entries' descriptions. Split entries count their part, and nothing names the other parts. The page is from the workspace, from the person who did the work (only while the period holds one person's time, else the workspace) or from a name the link was given. Unless a link is set to show today's time, it counts up to yesterday while today is in its period (`countedTo`). The token is kept as it is so admins can copy the link again; a new address or removing the link stops the old one. A read-only organization's links answer 403 (`urn:spindle:problem:shared-report-unavailable`).
- **Agent activity** is personal, not workspace data: the repository links the Mac and Windows apps keep (with their branch rules, `AgentRepositoryLinks.BranchRules`, a `jsonb` list of pattern, project and task), kept split suggestions, the repositories the person ignores (only as HMAC-SHA256 hashes keyed by their ID, `IgnoredRepositories`), and, only if the person turns on activity sync, the prompt times and runs it read from agent logs. It lives under `/api/me/agent-activity/…`, plain tables deleted for good, never shown to admins or in reports. What a workspace says about it (split suggestions with their evidence, untracked agent time for the calendar, the projects agents worked in lately) is only ever about the caller's own entries and days, worked out on request and never stored. See [splits-and-suggestions.md](splits-and-suggestions.md).
- **Subscriptions** (`src/Spindle.Api/Subscriptions`): on the hosted service (`Subscriptions:Enabled`), every organization made at sign-up starts a trial, and `OrganizationSubscriptions` says what it may do now: full access, or read-only once its trial or plan has ended. A self-hosted server keeps the rows but limits nobody. Once its trial or plan has ended, changes in its workspaces get 402 with the problem type `urn:spindle:problem:read-only`, except reports, stopping the timer, removing members, revoking invitations and the person's own agent activity (`.AllowWhenReadOnly()`). Seats are the people in at least one of an organization's workspaces. `TrialReminderService` emails owners and admins two weeks and three days before the trial ends and when it has; each reminder is claimed on the subscription row before it is sent, so it goes out once. The name is not "billing", which means billing clients.
- **Paying** (`SubscriptionBilling`, behind `ISubscriptionProvider`; Paddle is `PaddleProvider`, configured under `Subscriptions:Paddle`): our `OrganizationSubscription` decides what an organization may do, and the provider only reports payments. The server prepares each checkout (`POST /organizations/{id}/subscription/checkout`) with a price made for it: the catalog amount, the seats fixed, and the days left of our trial as Paddle's trial, so nothing is charged before it ends. Paddle's webhooks (`POST /api/subscriptions/webhooks/paddle`, signed with the destination's secret and taken only from the addresses Paddle lists at `GET /ips`, asked for hourly; behind a proxy that needs `ReverseProxy:KnownNetworks`) are taken in once per event (`ProviderEventReceipts`) and never let older news overwrite newer. After a plan is chosen, a few seconds after someone joins, is removed or deletes their account (`SeatChanges`, in the background), and hourly in `SubscriptionSyncService`, the subscription is brought in line with ours: the catalog price of the organization's price cohort, the current seats (settled with the next bill), and the first charge at the exact end of the trial; Paddle takes the items and the date only in separate requests. Deleting the last account of an organization cancels its plan. The customer portal (`…/subscription/manage`) handles cards, invoices and canceling. **Price cohorts**: every organization joins `Subscriptions:CurrentPriceCohort` at sign-up and keeps it for good (`OrganizationSubscription.PriceCohort`); each cohort has its own monthly and yearly catalog prices under `Subscriptions:Paddle:PriceCohorts:{name}`. Checkout and reconciliation use the organization's cohort, never the current one, so changing the current cohort changes the price for new organizations only. A subscription whose cohort is missing from the settings is left alone and logged, and its organization can't start a checkout.
- **Operators** (`src/Spindle.Api/Operator`): the people who run a server are listed by email in configuration (`Operators:Emails`), never in the app, and count only with a confirmed email. To anyone else `/api/operator/*` doesn't exist (404). They see organizations' metadata (owner, seats, subscription, last activity), never time, projects, clients or money, and every trial or comp they set is kept in `SubscriptionChanges`.
- **Agent proposals** (`AgentProposals`, `/api/workspaces/{id}/agent-proposals/…`): entries and changes the person's agents propose, waiting for the person, and like agent activity theirs alone: only their own entries, never shown to admins or in reports, plain rows deleted a week after they were dealt with. The server reads what an agent sends (times as text, in the person's time zone or with an offset) and refuses with a reason what can never be saved; listing says what saving each would store and what stands in its way; `apply` saves one through the same checks as saving an entry, in one transaction with marking it. Changes reach the person's devices with the sync topic `agentProposals`.
- **Agents over MCP** (`src/Spindle.Api/Mcp`, `/mcp`): an OAuth 2.1 authorization server for MCP clients (client ID
  metadata documents or dynamic registration, PKCE, consent on the web app's `/connect`) and the agent tools over
  Streamable HTTP. An agent let in is a device session for one workspace with `read` or `read write` scopes; its access
  tokens are for the MCP server's URL alone, its refresh token renews only at `/oauth/token`, and every MCP request
  checks the session is still signed in. Tools call the API's own handlers. How people connect
  their agents is in [connect-agents.md](connect-agents.md).
- **Live sync**: after every save, the API tells connected apps what changed (SignalR hub at `/api/hubs/sync`), and they load it again. Each app hears about its own account and the workspace it shows; the device that made the change is left out. The message only names what changed, so the data itself is always read through the API and its checks.
- **Live Activity pushes** (`src/Spindle.Api/Push`, Spindle Cloud only, configured under `Push:Apns`): the iPhone sends the push token of the Live Activity it shows, for its device session (`PUT /api/me/push-device`, a `PushDevices` row keyed by the refresh token family). After a save that changes someone's entries, `LiveActivityPushService` brings each of their iPhones in line with the running timer through APNs: it updates the activity while its entry runs and ends it once the entry stops, without an alert, so nothing sounds. A timer started elsewhere isn't pushed, since starting an activity by push needs an alert; the app shows it when opened. Nothing goes to the device session that made the change, nor what it was sent last. The content state is the app's `TimerActivityAttributes.ContentState`, its start in seconds since 2001 as Swift decodes a date. Devices whose session was signed out or lapsed are deleted, and so are tokens APNs no longer knows. Without the settings nothing is registered or sent.
- **Import**: admins bring time over from the detailed CSV reports of Toggl Track, Clockify, Harvest or Spindle. Columns are found by name, the date order is worked out, and a preview shows everything before anything changes. Harvest exports hours without times of day unless an account tracks start and end times, so each person's entries on a day are placed one after another from 9:00 (earlier on a day of more than 15 hours), and the preview says so. People are matched to members by email (or name, such as Harvest's first and last name), and can be assigned by hand. Existing clients, projects, tasks and tags are reused by name, and entries that are there already are skipped, so importing the same file twice adds nothing. A placed entry counts as there already when its person has one that day as long and described the same.
- **Exports** (CSV, Excel, PDF) are made on the server, so every app gets the same files. PDFs use the Geist font built into the API (SIL Open Font License, `src/Spindle.Api/Reports/Export/Fonts/OFL.txt`), so they look the same on any server.
